# Ingestion & Scraper Agent

## Manual upload path

1. User uploads a raw CSV/Excel file via the Next.js UI.
2. File is streamed to disk under a per-user storage root; a `UploadedFile` row is created (`sourceType: manual_upload`).
3. User selects (or the system infers from filename/columns) which `TargetSchema` this file should be cleaned against.
4. Proceeds into the cleaning pipeline ([04-ai-cleaning-and-audit.md](./04-ai-cleaning-and-audit.md)).

This is also the path for scraper output that only arrives as an emailed export (see [00-overview.md](./00-overview.md)) — the user downloads the email attachment and uploads it exactly like any other raw file. No special-casing needed in v1.

## Scraper agent path

Grounded in the two real examples in `/example-scrapers` (House Call Pro), which already show the range of variation the agent has to handle:

| | `housecallpro-job-attachments-scraper-v2` | `HouseCallPro` (exporter) |
|---|---|---|
| Runtime | Python (`pip3 install` + Playwright) | Node.js (`npm install`, requires a specific Chrome path) |
| Config | `.env` (email/password) | `housecallpro.env` (email/password/flags) |
| Invocation | Single script, no flags | `--only contacts,jobs,invoices` category selection |
| Output | Files on disk (`output/{COMPANY}/{job}/{file}`), then a separate zip/package step | Local `.xlsx` for invoices/estimates; **email** for everything else |
| Operational quirks | Rate-limit backoff, resumable via checkpoint files, session reuse | Headless flag for first-run 2FA, session dir reuse |

The agent cannot hardcode per-platform logic for 7 different scrapers — it has to actually read and reason over each README at run time. That's the core design constraint for this module.

### Workflow

1. **Install + Registration (one-time, human-assisted):** a scraper's files reach the scrapers root one of two ways — dropped in by hand (how the two `/example-scrapers` examples got there), or uploaded as a `.zip` through `/scrapers` (`lib/scrapers-fs.ts`'s `extractScraperZip`), which handles both a single wrapping folder and files at the zip root, and refuses zip-slip path-traversal entries before anything touches disk. Either way, an admin/user then registers a `ScraperDefinition` — points at the script + README paths. A human confirms the saved session/credentials are valid (2FA, interactive login) *before* the agent is allowed to trigger it unattended. The agent never performs interactive login itself.
2. **Trigger:** user (or future scheduler) asks the agent to run a specific scraper, e.g. "pull the latest House Call Pro job attachments."
3. **Plan:** the agent reads the `README.md`, extracts the run command(s) and any required flags (e.g. `--only invoices`), and produces a command plan. This is a distinct LLM call from the cleaning-script generator — see [05-llm-prompting.md](./05-llm-prompting.md) for why the two need different system prompts.
4. **Sandbox-execute:** the planned command runs inside a Docker container (see [06-security-sandboxing.md](./06-security-sandboxing.md)) with the scraper's own directory mounted — including its saved session file / `.env` — so it can authenticate without the agent ever seeing the plaintext credentials in its own context.
5. **Monitor:** the agent tails stdout/stderr and pattern-matches against README-documented signals it was told to watch for (e.g. HCP v2's `RATE-LIMITED` lines, `PROGRESS ... N errors` counter) to decide whether to let it keep running, or that it's stalled/failing and needs to stop and report to the user. This is intentionally generic — the "signals to watch for" come from what the agent parsed out of the README, not a hardcoded per-scraper switch statement.
6. **Ingest:** once the run completes (or a checkpointed partial run is stopped), the agent inspects the documented output structure and walks the resulting files, creating `UploadedFile`/`Attachment` rows mapped to the right customer/job/invoice per the README's stated layout.
7. **Log:** every step (plan, command executed, files ingested) is written to `ScraperRun` + `AuditLog`.

### Known hazards this design has to account for

- **README drift breaks the agent silently.** The HCP scraper's own history (v1 DOM scraper → v2 API scraper, because HCP changed URL structure) shows platform changes can invalidate a working scraper without warning. `ScraperDefinition.lastValidatedAt` plus surfacing scraper run failures prominently (not just logging them) is the mitigation — there's no way to fully automate around an upstream platform changing shape.
- **Rate limits are real and platform-specific.** Don't let the agent retry-loop into a 403 wall; respect documented cool-downs literally.
- **Checkpointed/resumable scrapers mean "run" isn't atomic.** A `ScraperRun` can represent a resumed continuation of a prior interrupted run — model status as `running | completed | interrupted | failed`, not just success/fail.

## Phase 5 build status

**Plan step — built and tested against the real HCP READMEs.** `POST /scraper/plan` reads a README verbatim (`app/scraper_fs.py`), sends it through a dedicated planning prompt ([05-llm-prompting.md](./05-llm-prompting.md)), and returns `setup_commands`/`run_command`/`watch_signals`/`confidence`/`concerns`. Verified against both real example scrapers (Python/Playwright HCP v2, Node HCP exporter) — the plan correctly picked up each one's distinct invocation style (flags vs. no flags, `pip3 install` vs `npm install`) straight from README prose, with no per-platform special-casing in the prompt.

**Sandbox-execute step — built and tested end-to-end against a safe synthetic fixture**, not a real platform (deliberate: this phase proves the *mechanics* — container launch, timeout, log capture, signal matching, new-file detection — without touching live scraper credentials). `POST /scraper/execute` (`app/scraper_sandbox.py`) ran a fake scraper that installs `requests`, makes one real HTTP call to `https://api.github.com`, writes a file under a nested output path, and prints a watched-for completion string. Result matched every expectation: `exit_code: 0`, `matched_signals` included the completion string, `new_files` correctly listed only the genuinely-new file (not the scraper's own `.py`/`README.md`/`.env`, which `list_files_modified_since`'s exclusion list correctly filtered out). See [06-security-sandboxing.md](./06-security-sandboxing.md) for the one real permission issue found while testing this (a test-harness mistake, not a code bug) and the fix.

**v1 simplification, stated up front rather than discovered as a gap:** monitoring is a post-hoc scan of the fully-captured log against `watch_signals` after the container exits (or times out), not real-time streaming with an early-abort on a rate-limit signal mid-run. Real-time streaming is a reasonable future improvement (`container.logs(stream=True)`), not implemented in v1 — a run that hits a rate limit still runs to its own timeout rather than being cut short the moment the signal appears in its output.

**Next.js side — built and tested end-to-end through the real running app**, not just unit-level. `/scrapers` (`app/scrapers/page.tsx`) discovers scrapers on disk (`lib/scrapers-fs.ts`) and registers a `ScraperDefinition`; `/scrapers/[id]` (`app/scrapers/[id]/page.tsx`) fetches a fresh plan on demand, requires an explicit confirmation checkbox before the "Run scraper now" Server Action fires, and shows run history. Ingestion (`lib/scraper-ingest.ts`) routes each new file by extension: spreadsheet exports (`.csv`/`.xlsx`/`.xls`) get copied into `STORAGE_ROOT` and become an `UploadedFile` (`sourceType: SCRAPER`) so the existing cleaning pipeline picks them up unmodified; everything else is left where the scraper wrote it, under the scrapers root, and becomes an `Attachment` referencing that path directly — no unnecessary copy of binary media. v1 gap: `Attachment.jobId`/`customerId` are left null (parsing them out of a path like HCP v2's `output/{COMPANY}/{job}/{file}` would need either a hardcoded per-platform parser or a second LLM call, neither built this phase).

Verified via a real browser session (Playwright driving system Chrome, headless) against the live Docker Compose stack — logged in as the seeded user, registered the same safe fake-scraper fixture through the actual `/scrapers` UI, requested a plan (confidence: high, matched the README correctly), confirmed and ran it, and confirmed in Postgres: `ScraperRun.status = COMPLETED`, `filesIngestedCount = 1`, and the produced file correctly became an `Attachment` (not spreadsheet-shaped) with the right path — the on-disk file was independently confirmed to exist too. This is a real proof of the full chain: browser → Server Action → ai-service → Docker sandbox → filesystem → Postgres, not a mocked or partial test. All test rows/files were removed afterward.

**Not yet run:** any real platform scraper (House Call Pro or otherwise) against live credentials — that step requires explicit user go-ahead first, independent of whether the mechanics are proven.

## Zip upload — built and tested for real

Dropping a scraper's files into the scrapers root by hand doesn't scale to "add a scraper through the app" — `extractScraperZip` (`lib/scrapers-fs.ts`) is the actual upload path behind `/scrapers`' "Upload a scraper" form. It handles both zip shapes people actually produce (a single wrapping folder, or files at the zip root with no wrapper) by checking whether every entry shares one common first path segment; whichever shape it is, the result lands as one top-level directory under the scrapers root, indistinguishable from a hand-copied one to `discoverScrapers()`.

Since this accepts arbitrary user-uploaded archive content, it's checked for the classic **zip slip** vulnerability (an entry path like `../../etc/whatever` writing outside the intended directory) — every entry's raw path is validated before anything is written, and the final resolved path is checked again after stripping a possible wrapping folder, since either step alone could otherwise let a traversal through. A duplicate directory name is rejected outright rather than silently overwritten — re-uploading (or a name collision with an existing registered scraper) fails with a clear error instead of clobbering session/credential files that might already be sitting in that directory.

**Verified for real**, not just by code review: uploaded a wrapped zip and a no-wrapper zip through the real running app (via a direct POST to the Server Action, replicating exactly what the browser's `<form>` submits) — both extracted correctly and showed up in "Discovered, not yet registered" exactly like a hand-copied scraper. Re-uploading the same zip was correctly rejected as a duplicate. A crafted zip with a `../../../../tmp/...` entry was correctly rejected before extraction, and independently confirmed the target file was never written anywhere on disk. All test scrapers removed after.

This did require loosening `web`'s scrapers mount from read-only to read-write (`docker-compose.yml`) — `web` still never *executes* a scraper or reads its credentials, that stays `ai-service`'s job in the sandbox executor (`docs/06-security-sandboxing.md`); it can now write new scraper directories, which is a narrower privilege than "run arbitrary code," but is a real change from the read-only guarantee stated through Phase 5, worth being explicit about.

## Credentials entry through the plan flow — built and tested for real

Every scraper example on hand takes an email/password in some `.env`-shaped file, but each one names the file and its variables differently (docs/05-llm-prompting.md's earlier table: HCP v2's `.env` vs. the exporter's `housecallpro.env`). Rather than hardcode either shape, the planning LLM call (`build_scraper_planning_prompt`, `apps/ai-service/app/prompting.py`) now also extracts `credentials_env_filename`/`credentials_env_template` straight from the README — the exact filename and `KEY=value` layout it documents, with `{{EMAIL}}`/`{{PASSWORD}}` placeholders standing in for the real values, using the README's own variable names rather than assuming `EMAIL`/`PASSWORD`. Both are `null` if a scraper documents no such file.

When a plan includes them, `/scrapers/[id]` shows Email/Password fields alongside the existing plan preview; leaving both blank on a run keeps whatever's already saved (an earlier manual setup, or a previous run's credentials) rather than clobbering it. Filling them in calls a new `POST /scraper/credentials` (ai-service) right before execution, which substitutes the placeholders and writes the file into the scraper's own directory (`write_credentials_env`, `apps/ai-service/app/scraper_fs.py`) — the model itself never sees or produces the actual email/password values, only the shape of the file they go in, same "orchestrator mounts the credential file" principle as every other scraper credential path in this app.

**Verified for real**, not just by code review: extended the safe fake-scraper fixture to document a `login.env` file with non-generic variable names (`SCRAPER_EMAIL`/`SCRAPER_PASSWORD`, not `EMAIL`/`PASSWORD`) and to actually read and use it (refusing to run without it). Ran the full flow through the real app — the plan correctly extracted `login.env` with those exact variable names (not a hardcoded guess), the form correctly showed the fields, and after submitting real values the scraper's own log confirmed it read them correctly (`Logged in as tester@example.com (password length 20, never printed)`) and completed successfully. Independently confirmed the written `login.env` on disk matched exactly. All test data removed after.

## Deleting scrapers — built and tested for real

Two delete paths, matching the two states a scraper can be in:

- **Discovered, not yet registered** (`/scrapers`'s "Delete" button next to Register): removes just the on-disk directory via `deleteScraperDirectory` (`lib/scrapers-fs.ts`) — nothing in the DB yet to clean up. Re-derives "not registered" server-side rather than trusting the client only rendered the button for an unregistered entry, and redirects with an error instead if it turns out to already be registered (delete it from its own page instead, since that path also has run history to cascade).
- **Registered** (`/scrapers/[id]`'s "Danger zone", confirmation-checkbox-gated like the run form): deletes the `ScraperDefinition` row first — cascading to its `ScraperRun`s and their `Attachment`s at the database level (`ON DELETE CASCADE`, confirmed in the actual migration SQL, not just assumed from Prisma's schema-level defaults), with any `PresentationSession` pointing at one of those runs correctly falling back via `ON DELETE SET NULL` rather than erroring — then removes the scraper's files (including any saved credentials) from disk. DB row first, then files, so a file-removal failure doesn't leave a half-deleted registration still pointing at a (potentially already-gone) directory.

**Verified for real**: deleted an unregistered scraper through `/scrapers` and confirmed its directory was actually gone from disk (not just absent from the page — checked independently, since a stale/cached page render could otherwise look like a false confirmation). Registered a scraper, deleted it through its own "Danger zone," and confirmed both the `ScraperDefinition` row and its on-disk directory were gone afterward, with a correct redirect back to `/scrapers`.

## Real gap found in production: credentials extraction needs more than just the README

Found using the project owner's own real (not test) `HouseCallPro-Exporter` scraper, registered on the actual deployed server: its plan came back with `credentials_env_filename`/`credentials_env_template` both null, and no Email/Password fields showed up — even though the scraper obviously takes a login. The README's setup step was `cp housecallpro.env.example housecallpro.env   # fill in email/password`, which never spells out the actual `HOUSECALLPRO_EMAIL`/`HOUSECALLPRO_PASSWORD` variable names inline — those only exist in the separate `housecallpro.env.example` file, which `/scraper/plan` never read. The model correctly declined to guess at variable names it hadn't actually seen (exactly the "don't invent" instruction working as intended) — the gap was in what context it was given, not the model's judgment.

**Fixed**: `find_credentials_example_file` (`apps/ai-service/app/scraper_fs.py`) looks for a `*.env.example`/`*.env.sample`/`*.env.template`/`*.env.dist` file in the scraper's own directory (same directory as the README — derived from `readme_relative_path`, no new request field needed) and, if found, appends its content to what the planning LLM sees, clearly labeled as the likely credentials template. The prompt now explicitly tells the model to use that file's real content and the *actual* target filename (what the setup step copies *to*, not the `.example` name) rather than falling back to null just because the README's own prose didn't spell out the format.

**Verified for real**: reproduced the exact same README pattern (`cp widget.env.example widget.env`, no inline format) against a synthetic fixture — before the fix this would have returned null/null like the real HouseCallPro-Exporter case did; after the fix, the plan correctly returned `credentials_env_filename: "widget.env"` (the real target name, not `.example`) and the exact variable names from the example file, with the non-credential `HEADLESS=true` line correctly carried through untouched.

## Choosing what to run: full export vs. specific operations

Raised by the project owner looking at their own `HouseCallPro-Exporter` plan: it forced a single fixed `run_command` (e.g. just invoices+estimates) even though the README documents several distinct scripts (contacts, jobs/equipment/memberships, invoices/estimates, a merge step) — no way to ask for everything, or a different subset, without hand-editing the command.

The plan now includes `available_operations: [{label, command}]` — populated only when the README actually documents more than one distinct thing to run (separate scripts per category, or one script with selectable category flags); left empty for scrapers with no such choice (don't invent a breakdown that isn't there). `run_command` becomes the full-export default (every operation joined with `&&`) when operations exist. `/scrapers/[id]`'s run form renders one checkbox per operation, all checked by default — a full export out of the box — and the actual command executed is reconstructed from whichever are still checked at submit time (`formData.getAll("operations")`, joined with `&&`), falling back to the plan's single `run_command` for scrapers with no operation choice.

**Verified for real**: built a synthetic three-operation fixture (contacts/invoices/jobs, matching the real HouseCallPro-Exporter's shape) — the plan correctly extracted all three as separate selectable operations. Ran it through the actual `/scrapers/[id]` UI with "Jobs" unchecked and the other two left checked (the default): confirmed in Postgres that `ScraperRun.commandExecuted` included only the contacts and invoices commands, and independently confirmed only `contacts.csv`/`invoices.csv` were written to disk — `jobs.csv` correctly never got created.

## Real bug found running a real Puppeteer-based scraper: the Node sandbox couldn't get Chrome

The project owner actually ran their real `HouseCallPro-Exporter` scraper (Puppeteer-based) and it failed during `npm install` — Puppeteer's postinstall step tries to download its own Chrome build, and that download failed with `no zip archiver is available` (the Node sandbox's `node:22-slim` base has no `unzip`). Even with `unzip` added, downloading a full Chrome build on every sandbox run would still be slow and wasteful for something that doesn't need to change per run.

**Fixed**: `apps/ai-service/scraper-sandbox/Dockerfile.node` now installs Debian's `chromium` package directly (`/usr/bin/chromium` — same debian-not-ubuntu reasoning already documented in `spikes/zoom-presentation-bot`/`apps/zoom-bot-service`, since Ubuntu's `chromium` package is a snap stub that doesn't run in a container). `run_scraper` (`apps/ai-service/app/scraper_sandbox.py`) sets `PUPPETEER_SKIP_DOWNLOAD=true` and `PUPPETEER_EXECUTABLE_PATH=/usr/bin/chromium` for `NODE`-runtime scrapers, so Puppeteer skips its own download entirely and launches the bundled system Chromium instead.

**Verified for real**: built a synthetic Puppeteer fixture reproducing the exact failure (a real `npm install puppeteer` + a script that launches it and navigates to a real page) — before the fix, this failed the same way the real scraper did; after the fix, `npm install` completed cleanly with no download attempt, and the script successfully launched Chromium, navigated to `https://example.com`, and read back its real page title.

## Second real bug, same scraper: plan commands missing their interpreter

With the Chrome issue fixed, the project owner's next run hit `sh: 1: housecallpro-exporter.mjs: not found`. The plan had produced `run_command: "hcp-merge.mjs"` — a bare filename, not something `sh -c` can run on its own. The real README's "Scripts" section lists every script exactly this way (`` `housecallpro-exporter.mjs --only invoices,estimates` ``, `` `hcp-merge.mjs` ``, ...) and never shows a `node` prefix anywhere in the file — a human reader infers "run this with node" from the `.mjs` extension and context; the planning model had no equivalent signal to work from.

**Fixed**: `/scraper/plan` now takes the scraper's own already-registered `runtime` (`ScraperPlanRequest.runtime`, passed from `def.runtime` in `app/scrapers/[id]/page.tsx` — this was already known, just never sent) and prepends it to what the model sees (`THIS SCRAPER'S REGISTERED RUNTIME: NODE`). The prompt now explicitly instructs the model that every command it produces (`setup_commands`, `run_command`, and every `available_operations[].command`) must be complete and directly executable — prepend `node ` to a bare `.mjs`/`.js` filename when runtime is `NODE`, `python3 ` to a bare `.py` filename when runtime is `PYTHON`.

**Verified for real**: re-ran the plan against the exact real README (copied from the live server) with `runtime: "NODE"` — every command, including all 5 entries in `available_operations` (the fix also surfaced two operations a prior run had missed — `--only services,materials` and the merge step), now correctly starts with `node `.

## Third real bug, same scraper: the setup step was clobbering the credentials it just wrote

With the interpreter fix in, the project owner's next run got further — installed dependencies, ran — but the scraper itself reported `Auto-login failed. Set HOUSECALLPRO_EMAIL and HOUSECALLPRO_PASSWORD.` despite the form having real values filled in. Root cause: this scraper's setup step is `cp housecallpro.env.example housecallpro.env` (documented in its README, needed for a from-scratch checkout that has no `housecallpro.env` yet) — but the run flow already writes the *real* `housecallpro.env` via `writeScraperCredentials` **before** `executeScraper` runs `setup_commands`, so that `cp` step immediately overwrote the just-written real credentials with the `.example` file's placeholder values (`you@example.com`/`your-password`) right before the script ever ran. A file being written twice by two different parts of the same run, in the wrong order, silently discarding the real values — not a partial fix, an outright ordering bug.

**Fixed**: `app/scrapers/[id]/page.tsx`'s `runScraper` now strips any setup command that copies something onto the credentials filename (`cp <anything> <credentials_env_filename>`) whenever credentials are actually being written this run — the real file already achieves what that step exists for, so running it afterward can only cause harm. Scoped narrowly (matches only a `cp ... <exact filename>` pattern, only when `willWriteCredentials` is true) rather than broadly filtering "anything setup-related," so it doesn't accidentally drop an unrelated setup step that happens to mention the filename.

**Verified for real**: built a synthetic fixture reproducing the exact shape (a `cp login.env.example login.env` setup step, a script that refuses to run on placeholder credentials) — before this fix would have reproduced the same silent-overwrite bug; after the fix, `ScraperRun.commandExecuted` correctly shows the `cp` step removed, the script's own log confirms it read back the real submitted email, and the file on disk after the run matched exactly what was submitted, not the template's placeholders.

## Fourth real bug, same scraper: scripts hardcoding their author's own Mac Chrome path

With credentials fixed, the next run got as far as actually launching a browser and failed with `Error: Browser was not found at the configured executablePath (/Applications/Google Chrome.app/Contents/MacOS/Google Chrome)`. Checked the real script: `hcp-contacts-joined.mjs` (and `hcp-remaining.mjs`, `housecallpro-exporter.mjs` — all three) hardcode `const CHROME = '/Applications/Google Chrome.app/Contents/MacOS/Google Chrome'` and pass it straight to `puppeteer.launch({ executablePath: CHROME, ... })` with no environment-variable override at all — `PUPPETEER_EXECUTABLE_PATH` (the earlier Chrome-download fix) does nothing for a script that never reads it, since the path is a literal constant, not a fallback.

**Fixed at the sandbox level, not by editing the scraper's own code** — that script is the scraper owner's own logic, not something this project should silently rewrite. `Dockerfile.node` now creates the exact path the script expects (`/Applications/Google Chrome.app/Contents/MacOS/Google Chrome`) inside the sandbox image as a symlink to the real Chromium already installed there. Since all three of this scraper's scripts hardcode the identical Mac path, one symlink fixes all three without touching any of them.

**Verified for real**: confirmed the symlinked path launches the real Chromium directly (`--version` through that exact path string). Then built a synthetic fixture reproducing the precise failure — a script with `executablePath` hardcoded to that same literal Mac path, no env-var fallback — and ran it through the actual sandbox execution endpoint: launched successfully, navigated to a real page, read back its title, completed with exit code 0.

## Fifth real bug, same scraper: login session/output going to an ephemeral path

With Chrome launching, the next real run got further still (browser opened, navigated to HouseCall Pro) but `hcp-contacts-joined.mjs` crashed with `TypeError: first.data is not iterable` — its own API call came back empty because there was no valid logged-in session. Reading the actual scripts: `hcp-contacts-joined.mjs` does no login of its own, it only reuses a browser profile at `process.env.HOUSECALLPRO_SESSION_DIR` (unset by default — the `.env.example`'s own `# HOUSECALLPRO_SESSION_DIR=...` line ships commented out). `housecallpro-exporter.mjs` *does* attempt an email/password login, but its default session path falls under `$HOME` — which `scraper_sandbox.py` sets to `/tmp` for an unrelated reason (npm/pip need a writable `$HOME` for an arbitrary sandboxed uid) — and `/tmp` is wiped when each sandboxed container is removed. Confirmed with the project owner that the account itself has no 2FA/CAPTCHA, so a headless auto-login should work *if* it had somewhere real to persist to.

**Fixed generally, not as a HouseCallPro special case**: the credentials-extraction prompt (`build_scraper_planning_prompt`) now also looks at commented-out optional variables in the credentials example file, and — only for ones whose name suggests a persistent-state or output path (`SESSION`, `PROFILE`, `USER_DATA`, `CACHE`, `COOKIE`, `OUTPUT`, `DOWNLOAD`) — uncomments them and points them at a short relative path under the scraper's own working directory (e.g. `.session`, `./output`) instead of leaving them unset or pointed at the example's own placeholder path. Unrelated optional settings (flags, display names, category filters) are left exactly as the example file has them.

**Also found and fixed while verifying this**: a real login session directory (a Puppeteer/Chrome profile) holds dozens of cookie/local-storage/preference files — before this fix, all of them would have looked like "new output" to `list_files_modified_since` and gotten ingested as bogus `Attachment` rows pointing at Chrome-internal binary state, not scraped customer data. Fixed by excluding any hidden (dot-prefixed) directory from ingestion, not just the specific named exclusions already in place.

**Verified for real**: confirmed the actual plan against the real README + example file now uncomments and sets `HOUSECALLPRO_SESSION_DIR=.session` / `HOUSECALLPRO_OUTPUT_DIR=./output`, leaving the unrelated `HOUSECALLPRO_CUSTOMER_NAME` line untouched. Then proved the underlying mechanism directly: ran a synthetic script that writes a session token to a relative `.session/` path in one sandboxed execution, then a **separate** execution (a genuinely different container) successfully read that same token back — confirming persistence actually survives across runs, not just within one. Confirmed the session directory itself is correctly excluded from `new_files` afterward, so it won't pollute ingestion once this is a real multi-file browser profile.

## Sixth real bug, same scraper: a real navigation timeout, and a status bug it exposed

The next real run failed with `Navigation timeout of 45000 ms exceeded` — the very first thing `housecallpro-exporter.mjs` does (`ensureLoggedIn`'s initial `page.goto` to `/app/home`, before login is even attempted). Reproduced the exact navigation against the real site from inside a container with the sandbox's own constraints (same `cap_drop`, `no-new-privileges`, non-root uid, 1 CPU, 1g memory, default 64MB `/dev/shm`, both a fresh profile and a copy of the scraper's real persisted `.session` profile) — it consistently completed in 13-15 seconds, well under the 45s budget. No systemic cause found; this looks like a one-off network/server hiccup against a real third-party site, which is an expected occasional reality of browser automation and not something to chase further without it recurring.

**A real, separate bug found while investigating**: every scraper run in the UI — including this one and, on inspection, every prior run in the database — was showing status `COMPLETED` regardless of whether it actually succeeded. Root cause: `run_scraper()` in `scraper_sandbox.py` read `container.attrs.get("State", {}).get("ExitCode")` right after `container.wait()`, but `docker-py`'s `Container.attrs` is a snapshot taken when the container object was created (i.e. the instant it started) and is never refreshed automatically — reading it without calling `container.reload()` first always returns the pre-run placeholder, `ExitCode: 0`, no matter how the container actually exited. Confirmed directly against the real Docker API on the server: a container that ran `exit 1` still reported `ExitCode: 0` without a `reload()`, and `1` with one.

**Fixed** by calling `container.reload()` before reading `State.ExitCode`. This was silent because nothing downstream depended on an accurate exit code failing loudly — the run's `logOutput` always showed the real error text, so the mistake only showed up as a wrong badge in the UI, not a crash.

## Seventh real bug, same scraper: the account has 2FA, and the login check couldn't tell

## Eighth real bug, same scraper: session-dependent operations running before the operation that logs in

With login working, the next real run failed with `TypeError: first.data is not iterable` inside `hcp-contacts-joined.mjs` — the exact same symptom as an earlier bug in this log, but a different cause this time. This scraper's README says one specific script does the real interactive login and persists the session; the others ("Contacts", "Jobs/Equipment/Memberships") do no login of their own, they only reuse whatever session already exists. This run's plan happened to order `hcp-contacts-joined.mjs` (session-dependent, no login) *before* `housecallpro-exporter.mjs --only invoices,estimates` (the one that actually logs in) in the `&&`-joined command — so it ran against zero session and got an auth failure the script doesn't handle gracefully (`apiGet` returns `{__error: status}` on a non-OK response rather than throwing, so the caller's `[...first.data]` blows up on `undefined`).

A human unchecking the login operation entirely is still possible and still their call; this only fixes the ordering among whatever's selected.

**Verified for real** against the actual README: re-ran `/scraper/plan` against it three times after the fix — the two that completed both put "Invoices + Estimates" (the session-establishing operation) first in `available_operations`, ahead of "Contacts" and "Jobs/Equipment/Memberships".
